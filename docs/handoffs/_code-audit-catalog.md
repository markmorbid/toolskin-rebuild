## 1.1 `TOOLSKIN_IONICONS_710` — const object (line 31)
- **Type:** global object literal (assigned `g.TOOLSKIN_IONICONS_710` inside an IIFE at line 30).
- **Purpose:** Auto-generated Ionicons 7.1.0 cheatsheet registry.
- **Shape:**
  - `version: '7.1.0'`
  - `flags: { <base-name>: <bitmask> }` — bitmask `1=filled, 2=outline, 4=sharp`. Hundreds of entries; nearly all are `7` (all three variants). Comment: "base name -> bitmask".
- Generated by `scripts/parse-ionicons-cheatsheet.mjs` (per comment line 29).

## 1.2 `ToolskinIonIcons` — const object (line 549)
- **Type:** const object, also exposed as `window.ToolskinIonIcons` (line 591).
- **Purpose:** Ionicons variant registry helpers (filled/outline/sharp resolution).
- **Constants:** `FILLED: 1`, `OUTLINE: 2`, `SHARP: 4`.
- **Public API:**
  - `registry()` → returns `window.TOOLSKIN_IONICONS_710` or `null`.
  - `flags(base)` → number bitmask; returns `FILLED|OUTLINE|SHARP` (7) when registry/base missing, `0` when base unknown.
  - `hasFilled(base)` / `hasOutline(base)` / `hasSharp(base)` → boolean.
  - `listBases()` → sorted array of base names.
  - `resolveIonIconName(base, opts)` → string; `opts = { outline?, sharp? }`; sharp wins over outline; falls back to filled, returns `''` when base falsy or no filled variant.

## 6.3 `_toolskinApplyContrastToTokenMap` — Color.js tension-slider logic
Function at `toolskin.js:1009`. Signature `(map, tension01)`. **Requires the `Color` global (colorjs.io).** Returns `false` if `Color` is undefined or `map` falsy; `try/catch` returns `false` on any error.

Verbatim algorithm:
```
t = clamp(Number(tension01) || 0, 0, 1)
tp = map['ts-text-primary']            // text primary
tb = map['ts-bg-body']                 // body bg
b1 = map['ts-bg-1'] || tb
b3 = map['ts-bg-3'] || tb

wSec       = 0.12 + t * 0.38           // secondary mix weight
wMut       = 0.28 + t * 0.42           // muted mix weight
wAnchorMid = 0.35 + t * 0.30
wAnchorDeep= 0.20 + t * 0.45

P  = new Color(tp)
B  = new Color(tb)
B1 = new Color(b1)
B3 = new Color(b3)

anchor     = B.mix(B1, wAnchorMid,  { space:'oklch' })
anchorDeep = anchor.mix(B3, wAnchorDeep, { space:'oklch' })

sec = P.mix(anchor,     wSec, { space:'oklch' }).to('srgb').toString({ format:'hex' })
mut = P.mix(anchorDeep, wMut, { space:'oklch' }).to('srgb').toString({ format:'hex' })

map['ts-text-secondary'] = sec
map['ts-text-muted']     = mut

bg2  = map['ts-bg-2'] || tb
bg2c = new Color(bg2)
map['ts-bg-2'] = bg2c.mix(anchor, 0.06 + t * 0.06, { space:'oklch' }).to('srgb').toString({ format:'hex' })
return true
```
Effect: at higher `tension01`, secondary/muted text are mixed harder toward the (oklch-blended) surface anchor, and `bg-2` is nudged slightly toward the anchor. All mixes use `space:'oklch'`. The function MUTATES the passed-in `map` in place.

> **This is the function the task brief flags as the spec-vs-code conflict point.** It depends on the colorjs.io `Color` class and its `.mix(..., {space:'oklch'})` / `.to('srgb')` / `.toString({format:'hex'})` API. Any engineering spec describing this contrast slider must match this exact dependency and weighting math.

## 6.7 Font Awesome version-detection — ACTUAL behavior (known-bug item)
File `toolskin-assets.js`. **Cataloguing the code as written — NOT fixing it.**

What the code actually does:
1. **No live version detection for Font Awesome.** The FA asset is registered (lines 359–376) with a **hard-coded literal `version: '6.7.2'`** and NO `cdnjsName` / `fallbackVersion`. In `_loadAsset` (lines 199–237), the version-resolution branch only runs `resolveVersion()` when `asset.version === 'latest' && asset.cdnjsName`. Since FA's version is the literal `'6.7.2'` (≠ `'latest'`) and there is no `cdnjsName`, the `else if (asset.version && asset.version !== 'latest')` branch fires and `version` is set directly to `'6.7.2'`. **The cdnjs API is never queried for Font Awesome.**
2. **The only "version" logic that touches FA is a cache purge.** At module load (line 187, top-level), unconditionally: `try { localStorage.removeItem('ts-cdn-font-awesome-version'); } catch(_) {}`. The in-code comment says: *"Purge stale version cache from previous 'latest' resolution that may have cached FA 7.0.1"*. So the code clears a cache key (`ts-cdn-font-awesome-version`) that, given the current pinned registration, is **never written** — `setCachedVersion` is only called from `resolveVersion`, which FA never reaches.
3. **`FONT_MAP.fontawesome` lists both FA6 and FA7 family names** (lines 176–184): three FA6 entries (`Font Awesome 6 Free` 900/400, `Font Awesome 6 Brands` 400) plus one FA7 entry (`Font Awesome 7 Free` 900). The comment frames the FA7 entry as "forward-compat" that will "resolve immediately if FA7 isn't loaded". `waitFonts('fontawesome')` calls `document.fonts.load()` for each — all `.catch()`-swallowed.
4. **The CSS-side family token is mixed-version.** `--ts-fontawesome-family: "Font Awesome 6 Free", "Font Awesome 7 Free"` (`toolskin.css:242`) lists both family names as a font-family fallback list.

**Net observable behavior:** FA is always loaded from cdnjs at the pinned `6.7.2` (CSS `all.min.css` + the three FA6 woff2 fonts). There is no runtime detection of which FA version is present; the system declares both FA6 and FA7 family names in `FONT_MAP` and in `--ts-fontawesome-family` as a static forward-compat hedge, and it purges an FA version-cache key that the current pinned registration never populates. The in-code comments describe a "version safety audit" intent (FA pinned because FA7 renames font families and breaks Unicode `content:` icon rules) — see `toolskin-assets.js` lines 356–385.

# 7. Notable discrepancies & observations

Factual observations only — cataloguing what the code does, not proposing fixes.

1. **Font Awesome has NO version detection.** Despite `toolskin-assets.js` having a full cdnjs `resolveVersion()` mechanism, Font Awesome is registered with the hard-coded literal `'6.7.2'` and no `cdnjsName`, so the API path is never taken for FA. The module unconditionally purges `localStorage['ts-cdn-font-awesome-version']` on every load — a key that the current pinned registration never writes. `FONT_MAP.fontawesome` and the `--ts-fontawesome-family` CSS token both list FA6 + FA7 family names as a static forward-compat hedge. (Full detail in §6.7. This is the brief's "known bug" item — described as-written, not corrected.)

2. **`--ts-fs-base` is declared twice in the master `:root`** (`toolskin.css:286–287`): `--ts-fs-base: 0.8rem;` immediately followed by `--ts-fs-base: 13px;`. Per CSS cascade the second (`13px`) wins; the `0.8rem` declaration is dead.

3. **`--ts-this-bg` and several `--ts-this-bg-*` tokens are declared multiple times** within the same `:where(:root, :root *)` block (`toolskin.css:976` & `984` for `--ts-this-bg`; `--ts-this-bg-bright` 3×, `--ts-this-bg-dark` 2×, `--ts-btn-pad-x/-pad-y/-fs` 2× each). Later declaration wins each time — the earlier ones are intentional-looking overwrites (some switch from a `#ffffff`-mix to a `var(--ts-bg-body)`-mix or to a token-driven percentage).

4. **`--ts-text-accent` is declared 2× more** at the end of the `:where` block (`toolskin.css:1061` and `1069`) after being aliased earlier — last wins.

5. **The Resizer `:root` block is duplicated verbatim** — `toolskin.css:2243` and `2262` contain identical `--ts-resize-enabled` + resizer-token declarations.

6. **`@keyframes ts-shimmer` is defined twice** (lines 10841 and a later ~22xxx region). Last definition wins.

7. **Spacing tokens `--ts-sp-17`…`--ts-sp-24` are flagged in-source as a "CRITICAL IMPLEMENTATION ERROR"** (`toolskin.css:442–457` REFACTOR NOTE) — the geometric multiplier produces 229px→1091px values the note says are unusable and should be removed/replaced. They are still declared and (per the note) "already distributed across the design system".

8. **`index.html` declares `window.__TOOLSKIN_CONFIG__` twice** (lines 88 and 109). The second declaration **reassigns the whole object** to `{ stylesheetDebugger:{ enabled:false } }`, so the first block's `cursor` / `reveal` / `smoothScroll` config is silently discarded. The effective init config for `index.html` is just `{ stylesheetDebugger:{ enabled:false } }`.

9. **The resizer global-disable selector is `:root[ts-resize="off"]`** (`toolskin.css:2283`) — a bare `ts-resize` attribute, NOT `data-ts-resize`. (Other framework hooks use the `data-ts-` prefix; this one does not.)

10. **`ToolskinIcons.inject` contains production debug logging** keyed on the literal text `'Surfaces Lab'` (`toolskin.js` ~2952–3059) — `console.log` blocks that fire whenever an icon-bearing element's `textContent` contains that string.

11. **`ToolskinTheme.setMode` sets two theme attributes** — both `data-theme` and `data-ts-theme` on `<html>`. CSS uses `[data-theme="light"]` for most rules and `[data-ts-theme="light"]` for a smaller set (tooltip, offcanvas). Both must stay in sync; `setMode` is the single writer.

12. **UIKit masonry uses a deprecated typo alias in its own `init`.** `TSUMasonryGrid` (typo, missing the 2nd `I`) is a `@deprecated` alias of `TSUIMasonryGrid` (toolskin-uikit.js:1142); `init()` at line 1155 calls the typo alias. Functionally equivalent (same function reference) but the public export exposes the correctly-spelled `MasonryGrid: TSUIMasonryGrid`.

13. **Two event-name prefixes coexist:** core `toolskin.js` dispatches `ts:*` events; `toolskin-uikit.js` dispatches `ts-ui:*` events. Any consumer wiring must use the correct prefix per module.

14. **Light mode is attribute-driven, not preset-array-driven at the CSS layer.** The CSS `[data-theme="light"]` block (`toolskin.css:27787`) hard-codes the `light-practical-clean-v1` values. The JS `ToolskinTheme` independently defaults to the same preset and writes inline `:root` styles. So light-mode surface values exist in TWO places (CSS block + JS preset) that currently agree but are not a single source of truth.

15. **`--ts-on-accent` auto-contrast threshold differs by mode.** `:where(:root,:root *)` uses `clamp(0,(0.75-l)*999,1)`; the `[data-theme="light"]` block first sets it with threshold `0.55` then re-declares it with `0.75` (last wins → 0.75 in both modes after the cascade). The OKLCH `oklch(from var(--ts-accent) … 0 0)` pattern picks white or black ink purely from accent lightness.
