## Verification protocol — MANDATORY

Every absorption merge that consumes a directive from this document must follow this sequence:

1. **Pre-merge Chrome visual capture.** Open the relevant section of the canonical showcase rendered against current `_NEW.css` in **Chrome browser** (not code preview, not IDE renderer, not other browser). Capture state.
2. **Apply the merge proposal.** Absorption subagent prepares the diff against `_NEW.css`.
3. **Post-merge Chrome visual capture.** Open the showcase against the proposed-merged `_NEW.css`. Capture state.
4. **Owner reviews captures side-by-side.** Approval requires visual parity OR visual improvement matching the directive's stated intent.
5. **Approved merges commit individually** with format: `absorb(canonical): <directive-section> → NEW.css`
6. **Rejected merges revert.** No patch-fixing. Owner directives can be re-proposed in a different form.

Code-side diffs alone are insufficient for any directive in this document.

## Directive 13 — `ts-section--overlay` is two components conflated

**Tag:** `@ts-component-consolidate`
**Target:** `.ts-section--overlay` and effect-layer family
**Discovered:** 2026-05-06 · mockup/index.html visual washout investigation

The current `.ts-section--overlay` class is overloaded with two mutually
exclusive responsibilities:

- **Job 1: surface tint** — applies background, consumes `--ts-this-bg-*`
  tokens, used for section accent colors and dim surfaces.
- **Job 2: effect-layer mounting point** — must remain transparent, hosts
  blend modes and filters, used for grain, glow, gradient effects.

These responsibilities are mutually exclusive at the cascade level. Any
selector trying to do both will eventually leak inheritance.

The current `:not(.ts-grain-layer)` exclusion rule is a patch that depends
on JavaScript reliably appending the `ts-grain-layer` class. This dependency
has proven fragile — the class is applied inconsistently across pages,
causing the mockup landing visual washout (grain blend-mode + parent overlay
blend-mode stacking, surface tint contamination of grain layer).

Phase 1 absorption MUST split into separate components:

- `.ts-section-tint` — surface tint job (background, --ts-this-bg)
- `.ts-effect-layer` — transparent effect mounting (blend, filter)
- `.ts-grain` extends `.ts-effect-layer` — adds noise SVG
- `.ts-glow` extends `.ts-effect-layer` — adds gradient

No `:not()` exclusions. No JS class dependency. Each component owns one
responsibility.

Symptom history:
- 2026-05-06: mockup/index.html grain layer washed out by parent overlay
  contamination; framed offset-rounded-bg layout retired same session
- Hero implementation continues to work because conditions happen to
  align there — not because the architecture is correct

Cross-references:
- Directive 1 (Scope consolidation required)
- Directive 7 (Structure unification required)
- Directive 10 (CSS logic removal — CSS becomes presentation only)

## Directive 14 — Gradient system is not a system

**Tag:** `@ts-component-consolidate`
**Target:** `.ts-section--glow` and gradient token family
**Discovered:** 2026-05-06 · mockup landing glow over-saturation

The current "gradient system" consists of three hand-authored glow values
(`--ts-accent-glow-bg`, `--ts-accent-glow-bg-2`, the chip-hover variant).
There is no parameterized control over:

- gradient ramp strength
- accent intensity
- dark stop balance
- opacity distribution
- mix percentages
- glow radius
- anchor positioning
- spread

Every gradient adjustment requires manually rewriting the entire
declaration. This is not consistent with Toolskin's three-tier token
discipline (Primitive → System → Component) and is not consistent with
the rest of the design system's derivative-math approach.

Phase 5 (component cycle execution) MUST design a parameterized gradient
system. Reference target shape (NOT for Phase 1 — Phase 5 only):

```css
:root {
  --ts-glow-anchor-x: 50%;
  --ts-glow-anchor-y: 0%;
  --ts-glow-radius: 60%;
  --ts-glow-strength: 0.4;
  --ts-glow-spread: 80%;
  --ts-glow-color: var(--ts-accent);
  --ts-glow-fade: var(--ts-bg-body);

  --ts-accent-glow-bg: radial-gradient(
    circle at var(--ts-glow-anchor-x) var(--ts-glow-anchor-y),
    color-mix(in oklch, var(--ts-glow-color) calc(var(--ts-glow-strength) * 100%), transparent) 0%,
    color-mix(in oklch, var(--ts-glow-color) calc(var(--ts-glow-strength) * 50%), var(--ts-glow-fade)) calc(var(--ts-glow-spread) * 0.5),
    var(--ts-glow-fade) var(--ts-glow-spread)
  );
}
```

Same approach for non-radial gradients (linear with anchor angles,
conic with start positions). All consumers reference the parameterized
output, not hand-authored stops.

Symptom history:
- 2026-05-06: mockup landing glow pushed too orange after recent
  `--ts-accent-glow-bg-2` introduction; reverting to `--ts-accent-glow-bg`
  partially restored composition

Cross-references:
- Directive 8 (Token ownership correction — tokens at component root)
- Phase 5 candidate (NOT Phase 1 absorption — too large)

## Aggregate principles distilled from the directives

These are the cross-cutting principles that emerge from reading all 12 directives together. The reconstruction's design-tokens-2.0 skill should reference these as authoritative:

1. **Token ownership lives at component root.** Leaf nodes consume only.
2. **State is JS-driven.** CSS styles `[data-state=…]` attributes — never derives state via `:has()` chains.
3. **App scopes can only override tokens.** Never structure, never state, never new components.
4. **Variants extend their base component.** No parallel implementations.
5. **`!important` is forbidden** — except where explicitly tagged `@ts-component-exception` with documented justification.
6. **Visual verification is browser-side, in Chrome.** Code-side diffs are necessary but never sufficient.
7. **If it breaks outside an app scope, the implementation is invalid.** Portability is the test.
8. **CSS is presentation only.** Any logic in CSS is a smell.
